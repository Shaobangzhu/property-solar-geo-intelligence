# Methodology and limitations

This PoC is a sequence of distinct claims. Passing software tests does not establish geographic, solar, or financial accuracy. The interface labels user inputs as assumptions and shows a single **Economics estimate unavailable** state until sufficient evidence exists. It does not render empty annual metric cards as if they were calculated results.

| Correctness layer | What is implemented | What is not established |
| --- | --- | --- |
| **Software correctness** | TypeScript checks, validation, local database constraints, API/component tests, snapshot CRUD, and build checks protect expected program behavior. | Automated tests mock ArcGIS and PVWatts; they do not prove live service availability, key privileges, real-world address quality, or customer-specific output accuracy. |
| **GIS correctness** | Stored ArcGIS geocoding requests use `forStorage=true`; precise address candidates are filtered; saved longitude/latitude are WGS84; the marker, outline, scene lighting, and ShadowCastAnalysis use those coordinates. | Address matching does not verify residential land use or ownership. A geocoded address point is not a surveyed parcel, roof centroid, or building footprint. The hand-drawn polygon is a visual outline. Terrain, building context, shadow coverage, and user-entered UTC offset can vary; no engineering-quality 3D roof or measured shadow-loss model is produced. |
| **Solar-model correctness** | PVWatts V8 receives property latitude/longitude, user-entered roof tilt/azimuth, system capacity/losses/module/array type; the backend returns twelve monthly AC kWh values, annual AC kWh, resource metadata where supplied, and warnings. | The app does not verify roof suitability, panel count, installation layout, measured irradiance, electrical design, performance guarantees, or long-term weather. Usable roof area does not size the system. The manually entered shading factor and ArcGIS shadows are not turned into a validated PVWatts loss. |
| **Financial-model correctness** | Historical bill dollars and annual household consumption kWh are stored separately. Reviewed SCE rate-input modules retain filing/source metadata; interval calculation primitives require explicit co-timed energy and self-consumption. | The app does not know the account's actual tariff, supply arrangement, PTO date, NBT vintage, hourly load and production, complete charge/credit ledger, or annual settlement. It cannot calculate defensible annual cost, solar value, grid imports/exports, export credit, or savings from the current inputs. |

## Calculation boundaries

**IMPLEMENTED — address and visualization.** The browser first asks the local API for a normalized-address match. A miss triggers an ArcGIS stored-geocoding request from the browser. Only sufficiently precise, unambiguous candidates are persisted. The saved coordinates drive the Map/3D marker and scene navigation. Optional Property fields are manual data, not geocoding attributes.

**IMPLEMENTED — roof and sunlight.** A Roof Profile stores usable area, tilt, azimuth, and an optional estimated shading factor as user-adjustable assumptions. A sketch, when present, is a small closed GeoJSON polygon in WGS84 and is displayed in Map/3D. Its planar shape and 3D placement do not measure roof surface area, slope, height, or obstructions. Date/time lighting shows a simulated sun. Direct shadows require available 3D casters; the optional 30-minute shadow overlay is bounded by the sketch and is a visual analysis. It is not annual insolation or kWh production.

**IMPLEMENTED — PVWatts.** Express calls the current PVWatts V8 monthly endpoint. It passes capacity, system losses, module type, array type, latitude, longitude, tilt, and azimuth. The application validates inputs and normalizes a response to twelve January–December AC kWh values and an annual AC kWh value, with warnings kept separate. The PVWatts API key stays backend-only. The output is a model estimate for the chosen assumptions; it does not validate whether the physical roof can host that system. A later PVWatts call may differ from a saved result because the external resource or model may change.

**IMPLEMENTED — electricity inputs and History.** Bill entries represent actual user-entered USD amounts for a selected historical year; empty entries become zero. They are not labeled “without solar” and are not used to infer exact kWh. Annual household kWh is an independent input. An AnalysisRun freezes the Property details and coordinates, roof/system assumptions, production values and warnings, selected bill year and values, and annual consumption. View restores that snapshot; Edit updates only the selected run. This reproduces the saved display, not necessarily the original external PVWatts calculation under future service data. Sunlight date/time settings are exploratory UI state and are not part of an AnalysisRun snapshot.

**IMPLEMENTED — verified tariff inputs, with a narrow boundary.** The supplied filed SCE TOU-D-PRIME sheets and NBT26 hourly export CSV were reviewed and encoded with version/source metadata. The server can select an eligible interval's import energy rate and gross export-credit price in limited cases; gross accrual is not an applied credit, bill reduction, or cash payout. The current annual Economics panel stays unavailable. Exact source sheets, effective dates, applicability limits, and the reviewed CSV checksum are in [utility economics methodology](utility-economics-methodology.md). Synthetic test fixtures are marked **TEST DATA — NOT CURRENT SCE RATES** and never supply runtime results.

## What an annual financial estimate would require

**PLANNED, not implemented:** confirm the customer's actual SCE billing program, bundled versus CCA/Direct Access supply, import plan, Original Permission to Operate date, export vintage and eligibility, exemptions, and billing period. Obtain time-aligned household demand and solar generation or a validated, clearly disclosed interval model. Apply the tariff revision effective for each interval, fixed and non-bypassable charges, allowed credit offsets and carry, annual settlement, and any compensation rules. Reconcile against an authoritative worked example or actual redacted bill before showing annual dollar results. A single timeless dollars-per-kWh multiplier would not satisfy these requirements.

**DEFERRED:** measured roof geometry, automatic roof extraction, automated obstruction/shading-loss derivation, and engineering-grade feasibility. **FUTURE:** broader utility coverage and additional properties only after the one-property model is verified. These are not part of the current PoC.

## Practical walkthrough limits

Local automated tests exercise domain and UI boundaries with mocked service calls. A live demonstration also needs the PostgreSQL container, migrated schema, a browser ArcGIS key permitted for stored geocoding/basemaps/elevation, a backend PVWatts key, and network access. A failure to load 3D building context should be described as missing context, not evidence that a property has no shadows. For addresses in another time zone or across daylight-saving transitions, set the scene's UTC offset deliberately; the app does not derive an authoritative property time zone. The application's current output should be described as a visual planning aid and a model-based production estimate, with financial outputs unavailable.
